# Governed R81.20 To R82 Build 777 And Bundled Take 60

This walkthrough covers a two-member ServiceNow-governed major upgrade from
R81.20 to an approved R82 Blink image whose resulting gateway build is 777 and
whose bundled JHF is Take 60. It follows the completed lab scenario but uses
only documentation addresses and placeholders.

This is not a package recommendation or a support statement. Confirm the image,
upgrade path, policy compatibility, licenses, and maintenance plan with your
Check Point support channel. The completed lab run had ICAP disabled, so it
provides no evidence about ICAP health during or after this upgrade.

Read the [shared governed operating guide](README.md) first. Use
[Start Here](../../docs/START_HERE.md), the
[component reference](../../docs/COMPONENT_REFERENCE.md), and the
[ticket example](../../docs/SERVICENOW_TICKET_EXAMPLE.md) for material that is
not repeated here. The [runner CLI walkthrough](../runner_cli/README.md)
documents the separate ServiceNow-free path.

## 1. Prepare The Approved Attachment

The checked-in [CSV template](r8120-to-r82-t60.csv) has invalid checksums and a
placeholder package identity. It must fail validation as shipped. Never edit it
in place. Create a protected working copy outside the checkout:

```bash
install -m 0600 \
  examples/governed/r8120-to-r82-t60.csv \
  /tmp/cpuse-r8120-to-r82-approved.csv
```

Replace the package name and both invalid checksum fields with values from the
approved image staged on the MDS. Independently compare the file size and hashes
with the publisher's records. Keep `action=upgrade`, `package_type=blink`, `target_build=777`, and
`reboot_expected=true`. The declared build is an exact post-mutation gate, not
a minimum. Do not attach a JHF install or removal row to this
request; the target image already contains its bundled Take.

## 2. Submit One Catalog Request

Use the configured catalog choices and attach the protected CSV with a filename
containing `CPUSE Package`. The JSON below shows the request-variable shape; it
is not an API payload and contains no record identifiers:

```json
{
  "activity_type": "version_upgrade_activity",
  "environment": "lab",
  "icap_mode": "disabled",
  "target_ips": "192.0.2.20\n192.0.2.21",
  "mds_host": "192.0.2.10",
  "current_version": "R81.20",
  "target_version": "R82",
  "cpuse_package_upload": "CPUSE Package - R82 Upgrade.csv",
  "preserve_original_active": "yes",
  "tester_gate": "yes",
  "scheduled_start": "<approved-start>",
  "scheduled_end": "<approved-end>",
  "cpuse_dependency_upload": "",
  "special_instructions": "Use the approved R82 build 777 image with bundled Take 60. Validate mixed-version policy gates and retain the tester pause."
}
```

Do not put credentials, MDS filesystem paths, execution switches, or a target
Take override in the ticket. The runner infers and validates package state from
the approved attachment and staged artifact.

## 3. Complete Readiness And Change Approval

Start and monitor the workers with the commands in the
[shared guide](README.md#what-the-operator-runs). Before moving the CHG to
Implement, require all of the following:

- the readiness SCTASK is Closed Complete and reports `ready` from the
  automated source;
- discovery resolves one two-member cluster and maps both requested TEST-NET
  addresses to the expected managed object;
- both members report R81.20, the intended original ACTIVE/STANDBY ownership,
  healthy pnotes, and matching monitored and virtual interface signatures;
- the staged Blink identity is unique and its SHA-1 and SHA-256 match the
  approved records;
- policy package, reboot expectation, CDT backend, tester gate, ownership
  restoration, and ICAP-disabled mode are visible in the generated plan;
- the CHG is approved, in Implement, and has exactly one open governed
  Implementation CTASK.

The operator does not launch `servicenow_checkpoint_runner.py`. The worker does
that after it revalidates these governance fields.

SYNTHETIC OUTPUT SHAPE - NOT LAB EVIDENCE

```text
Readiness: ready
Managed object: EXAMPLE-CLUSTER (two-member cluster)
Current release: R81.20
Requested target: R82
Package: one validated Blink upgrade row
Original roles: EXAMPLE-GW-A ACTIVE, EXAMPLE-GW-B STANDBY
ICAP mode: disabled
Evidence reference: <readiness-run>
```

## 4. Follow The First-Member Phases

The worker and runner execute these phases in order:

1. `discover-targets`
2. `validate-plan`
3. `init`
4. `deployment-agent-readiness`
5. `cluster-state-capture`
6. `baseline-capture`
7. `stage-files`
8. `first-member`
9. `mixed-version-policy-gate`
10. `mvc-on`
11. `failover-to-first`
12. `approve-testers`

Inside `first-member`, prerequisites run before CDT candidate generation and
guarded execution. Exactly one candidate must select the originally standby
member. After its reboot, reconciliation must show R82 build 777 and bundled
Take 60 before policy or failover work proceeds.

The mixed-version policy gate tests the required policy behavior while the
members run different releases. Treat each policy result as evidence; do not
replace this gate with a generic cluster-health check. The runner then enables
MVC and requires an exact `ON` readback before failover.

At `approve-testers`, the runner exits `20`. The worker records
`waiting_tester`, leaves the Implementation CTASK open, and waits for the
existing tester CTASK created by the ServiceNow business rule. It must not begin
the second member yet.

SYNTHETIC OUTPUT SHAPE - NOT LAB EVIDENCE

```text
first-member: completed
first-member reconciliation: R82 build 777, bundled Take 60
mixed-version-policy-gate: expected policy outcomes recorded
mvc-on: ON readback confirmed
failover-to-first: updated member is ACTIVE
approve-testers: waiting for dedicated tester CTASK
Runner return code: 20
```

## 5. Complete The Tester Gate

Create fresh evidence for this change. Do not reuse this empty template as an
approval record:

```text
Tester evidence checklist - EMPTY TEMPLATE
Change reference:
Tester name or accountable identity:
Test start and end time:
Updated ACTIVE member identity:
Current ACTIVE/STANDBY output attached: [ ]
Required interfaces and pnotes healthy: [ ]
Application and traffic tests listed: [ ]
Application and traffic results attached: [ ]
Policy behavior validated for the approved scope: [ ]
R82 build 777 and bundled Take 60 reconciled: [ ]
Decision (leave blank until testing is complete):
```

Keep the tester CTASK open if any box is incomplete or any result is unhealthy.
Only Closed Complete on the exact tester CTASK authorizes the worker to resume.

## 6. Resume And Verify Completion

The worker, not the operator, invokes the same change with
`--start-at second-member`. It reuses the original run lineage and proceeds:

1. `second-member`
2. `final-policy-install`
3. `mvc-off`
4. `restore-original-active`
5. `final-support-capture`
6. `support-diff`
7. `postcheck`

The second member repeats prerequisite, unique-candidate, guarded execution,
reboot, trusted reconnect, and exact version/Take reconciliation. The final
policy task must succeed for the target version. MVC must read back exactly
`OFF` on both members before completion. If requested, ownership returns to the
original A ACTIVE / B STANDBY arrangement.

SYNTHETIC OUTPUT SHAPE - NOT LAB EVIDENCE

```text
second-member reconciliation: R82 build 777, bundled Take 60
final-policy-install: Access Control and Threat Prevention tasks successful
mvc-off: OFF readback confirmed on both members
restore-original-active: original ownership restored
postcheck: errors=[] package_state_errors=[]
summary: completed
Worker return code: 0
```

Before ServiceNow closes the operational tasks, inspect the activity plan,
original cluster-state capture, both per-member action records, both
mixed-version policy outcomes, MVC `ON` and `OFF` readbacks, final policy task,
support diffs, and postcheck. Both members must show the exact target state;
success on only one member is not completion. Record explicitly that ICAP was
disabled and therefore was not validated by this run.
